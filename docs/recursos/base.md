# Base: como adicionar um recurso

A base (`main.js`, `preload.js`, `src/ipc`, `src/core/projects`, `renderer/app.js`, `renderer/features/shell.js`) já cuida de janela, IPC, modelo de projeto, abas, modais e salvamento. Um recurso novo é **um handler no processo principal + uma feature no renderer**. Contratos completos: [arquitetura.md](../arquitetura.md). A **interface** (tokens, componentes, menu lateral, telas largas/de trabalho, modo embutido, janela sem moldura) está em [interface.md](interface.md).

## 1. Handler (processo principal)

Crie `src/ipc/handlers/<recurso>.js`. Ele é carregado sozinho por `src/ipc/index.js` (todo `handlers/*.js`, em ordem alfabética). Se o arquivo falhar ao carregar, os outros continuam e o app mostra um aviso.

```js
'use strict';

function register(ctx) {
  // canal "<recurso>:<acao>" em camelCase; o payload chega como objeto ({} se vier vazio)
  ctx.handle('exemplo:somar', ({ a, b }) => {
    if (!Number.isFinite(a) || !Number.isFinite(b)) {
      const err = new Error('Informe dois números válidos.');   // português: causa + o que fazer
      err.code = 'INVALID_ARGS';
      err.details = { a, b };                                    // opcional
      throw err;                                                 // vira { ok:false, code, message, details }
    }
    return { total: a + b };                                     // vira { ok:true, total }
  });

  // evento do main para o renderer
  ctx.send('exemplo:progresso', { p: 0.5 });
}

module.exports = { register };
```

O que `ctx` oferece: `ipcMain, app, dialog, shell`, `getWindow()`, `send(canal, payload)`, `paths` (`userData, projects, tools, cache, downloads`, já criadas), `tools` (objeto vivo com `ffmpeg, ffprobe, ytdlp, whisper, twitchDownloader` — caminho ou `null`; use sempre `ctx.tools.x` na hora de usar, nunca guarde o caminho), `refreshTools({ force }?)`, `toolUsage` (`register(fn)`: declare que está usando uma ferramenta, veja [tools.md](tools.md)), `toolCatalog`, `projectStore`, `bus` (EventEmitter do main), `log(nivel, msg)`, `handle(canal, fn)`. `ctx.tools` prefere a ferramenta instalada pelo app (aba Ferramentas) e cai para `CORTE_*`/PATH; ffmpeg/ffprobe vêm só do sistema.

Regras: não grave o projeto aberto (só o renderer grava, via `BF.project.update`); estado que sobrevive sem projeto vai em arquivo próprio em `paths.userData`, com gravação atômica (tmp + rename); nunca apague nem sobrescreva arquivo do usuário. Sem a ferramenta necessária, devolva erro explicando como resolver (e a interface deixa a ação desabilitada).

## 2. Feature (renderer)

Crie `renderer/features/<id>.js` e `<id>.css`. Os ids da tabela 1.4 já estão no `index.html`; um id novo exige incluí-lo no `index.html` e na tabela (dono: base).

```js
'use strict';

(function () {
  const BF = window.BF;
  const { el } = BF.util;

  BF.ui.registerTab({
    id: 'exemplo', title: 'Exemplo', order: 35,
    badge: () => BF.state.project?.ext.exemplo?.total || '',
    render(container) {
      const botao = el('button', { type: 'button', onclick: somar }, 'Somar');
      container.append(botao);
    }
  });

  async function somar() {
    const res = await BF.api('exemplo:somar', { a: 1, b: 2 }, { toast: true });   // toast só com { toast:true }
    if (!res.ok) return;
    BF.project.update((project) => { project.ext.exemplo = { total: res.total }; }, { reason: 'exemplo:somar' });
  }

  BF.on('exemplo:progresso', ({ p }) => { /* evento do main */ });
  BF.bus.on('project:loaded', ({ project }) => { /* redesenhar a partir de BF.state.project */ });
  BF.hooks.add('beforeOpen', async (ctx) => { /* devolver false cancela a abertura do vídeo */ });
})();
```

O menu lateral tem 5 itens (Início, Projetos, Cortes, Exportações e Configurações; esta abriga Geral, Preferências e Ferramentas) e **onde a aba aparece** vem de `src/core/ui/menuLayout.js`: a aba de um recurso já conhecido entra no item dele (Cortes abriga Cortes, Análise, Legendas, Áudio e Exportar; Configurações, Preferências e Ferramentas) e uma aba que o layout não conhece ganha um **item próprio** no menu, na posição do `order`, com o ícone (`icon: 'nome_do_material_symbol'`; sem ele vale o padrão por id) e o selo dela. Opcionalmente a aba traz `view: 'wide' | 'work'` (largura total ou duas colunas com o player); veja interface.md. Ao criar um recurso, decida onde ele mora: se deve ficar dentro de um item que já existe (ou ser uma tela escondida de um item, como Novo projeto em Projetos), acrescente o id dele ao `LAYOUT` do `menuLayout.js`; se não, ele aparece como item próprio. O `tests/menu-layout.test.js` exige que as telas registradas por `renderer/features/*.js` sejam exatamente as do `LAYOUT`, para essa escolha nunca passar em branco. Use `BF.ui.confirm/prompt` (nunca `window.confirm`), `BF.ui.toast/log` para avisos e `BF.player` para tocar trechos. Dados do recurso no projeto ficam em `project.ext.<recurso>` (ou nos campos do contrato 2.1). Ao mudar cortes, emita `cuts:changed`; ao decidir algo sobre um corte, emita `decision`. Só dependa de `BF.*`, nunca de outra feature.

## 3. Testes

- Unitário: `tests/<recurso>*.test.js` (`node --test`). Para testar um handler sem abrir o Electron, monte um `ctx` com `createContext` e um `ipcMain` falso (veja `fakeElectron` em `tests/ipc-base.test.js`).
- E2E: `tests/e2e/<recurso>.e2e.js` com `tests/e2e/helpers.js`: `launchApp(userDataDir)` (porta de depuração dinâmica, perfil próprio; devolve `{ page, errors, stop }`), `waitFor(page, expr)`, `answerModal(page, true|false, { text })` para responder aos modais, `assertNoConsoleErrors(page)`, `makeSampleVideo(ffmpeg, arquivo)`, `mkTemp/removeDir` e `cleanupAll()` no `finally`. Use pastas temporárias `bf-…` e remova tudo ao final.

## 4. Lista de conferência

- Interface em português, poucos botões, ajustes avançados em `<details>`.
- Nada fictício: sem ferramenta/permissão, mostrar o motivo e desabilitar a ação.
- Lint limpo nos seus arquivos (`npx eslint <arquivos>`), testes do recurso passando, nenhum erro de console no e2e.
- Mudou um contrato? Registre em "Pedidos de contrato" do seu `docs/recursos/<recurso>.md` (a seção 5 de `arquitetura.md` é consolidada pela integração).

## 5. O que a base garante (comportamento)

Resultado da integração: o que cada pedaço da base promete aos recursos. Tudo abaixo foi executado de verdade (os testes citados estão no fim de cada item).

- **Uma instância por perfil** (`src/singleInstance.js`, ligado no `main.js` antes de `whenReady`). Abrir o app de novo com a mesma pasta de dados (um segundo clique no atalho) **não** cria outra janela: a segunda instância encerra sozinha e a primeira é restaurada (se estava minimizada) e focada. Sem isso duas janelas disputavam `queue.json` (a recuperação marcava como "interrompido" o que a outra ainda exportava), o `.part` e o projeto (o último a gravar vencia). É o que sustenta as premissas dos outros recursos ("o app abre uma janela só", `reserved` por processo, `profiles.json` sem trava). A trava é por `userData`: perfis diferentes continuam podendo abrir juntos (os e2e em paralelo dependem disso). Testes: `tests/single-instance.test.js` e o passo "segunda instância" de `tests/e2e/app.e2e.js`. A restauração da janela minimizada foi conferida à mão pelo Win32 (`ShowWindow`/`IsIconic`); o foco real não é verificado no e2e.
- **Procura de ferramentas sem `where`** (`src/core/ffmpeg/locate.js`). O PATH é varrido pelo Node (uma listagem por pasta, todos os nomes numa passagem). Pasta com acento (`João`, `Programação`) funciona (o `where.exe` escrevia na página de código OEM e o caminho voltava corrompido, então FFmpeg e ffprobe "sumiam" e abrir vídeo ficava bloqueado); a pasta atual do processo **não** conta (um `ffmpeg.exe` solto ali não é executado); entradas relativas ou vazias do PATH são ignoradas; `CORTE_*` precisa apontar para um **arquivo**; o PATH pode se chamar `Path`. Custo medido nesta máquina (ocupada): `resolveTools` de 30 a 76 ms (antes 2,1 a 3 s), `setupIpc` completo 250 ms (antes 4,9 s), `refreshTools` 50 ms (antes até 11,5 s). Testes: `tests/ffmpeg-locate.test.js` e o passo "João Programação" de `app.e2e.js`.
- **Ler o vídeo** (`src/core/ffmpeg/probe.js`). Falha do ffprobe vira `PROBE_FAILED` com mensagem em português que diz causa e solução ("o arquivo não parece ser um vídeo válido ou está incompleto… espere a gravação ou o download terminar…", "pasta ou acesso negado", "não foi encontrado", "ffprobe não executável", "demorou mais de 30 s"); a linha de comando e o texto em inglês vão **só** para `details.raw`. Arquivo sem vídeo = `NO_VIDEO` ("não contém vídeo"). A análise (`manager.js`) usa a mensagem do probe sem prefixá-la de novo.
- **Duração desconhecida**. MKV e WebM escritos em tempo real e nunca finalizados não têm duração no cabeçalho. `probeMedia` tenta, nesta ordem: o contêiner, os fluxos (campo ou tag `DURATION`) e, por último, a leitura dos pacotes de vídeo do arquivo inteiro (até 120 s; o resultado fica em memória por arquivo, tamanho e data). `info.durationSource` diz de onde veio (`format`, `stream`, `scan`, `unknown`). Se continuar desconhecida (`duration: 0`), `source:open` abre mesmo assim e devolve `warnings: [{ code:'DURATION_UNKNOWN', message }]`; a barra de marcação não aplica limite superior e diz isso. Testes: `tests/ffmpeg-probe.test.js` (MKV e WebM reais gravados em pipe), `tests/ipc-source-open.test.js`, `app.e2e.js`.
- **Projetos** (`src/core/projects/projectStore.js`). Gravação: tmp + `fsync` + rename (repetido em `EPERM`/`EBUSY`/`EACCES`); antes de substituir o arquivo, a última versão boa vira `<id>.json.bak` (um principal ilegível nunca vira o `.bak`). Falha de gravação lança `PROJECT_WRITE_FAILED` (português: disco cheio ou pasta em uso; o texto cru em `details.raw`). Leitura: só **JSON quebrado ou estrutura irreconhecível** conta como corrupção; uma falha de leitura passageira (`EBUSY` etc.) é repetida e, se persistir, vira `PROJECT_UNREADABLE` **sem mover nada**. Corrompido: o arquivo é preservado como `<id>.json.<epoch>.corrupt` (nunca apagado) e, havendo `.bak` íntegro, ele é restaurado como projeto principal. `source:open` devolve `recovered: { file, restoredFromBackup, backupAt }` e a interface **avisa** (toast longo mais barra de status) com o caminho do arquivo guardado; sem cópia o projeto recomeça vazio e o aviso diz isso e pede para não apagar o `.corrupt`. O aviso fica pendente no store (`loadDetailed` o consome) porque a conferência das Preferências (`prefs:inspect`) carrega o projeto antes de `source:open` e faria a recuperação sozinha. Testes: `tests/projectStore.test.js`, `tests/ipc-source-open.test.js`, `app.e2e.js`.
- **Salvar no renderer** (`renderer/app.js`). Se `project:save` falha, a edição continua na memória e o app **tenta de novo sozinho** (1,5 s, 4 s e depois a cada 10 s); o aviso aparece uma vez por sequência de falhas e, quando a gravação volta, mostra "Projeto salvo". **Trocar de vídeo** com a gravação falhando pergunta ("Abrir mesmo assim" / "Continuar neste vídeo") em vez de descartar a edição. Se algo for editado enquanto o vídeo abre, o projeto antigo é gravado antes de sair da memória e, no caso do **mesmo** vídeo (mesmo id), a versão da memória (mais nova que o disco lido pelo `source:open`) é mantida, só com os dados medidos do arquivo atualizados.
- **Tempos** (`src/core/projects/timecode.js`, universal: `window.BFTime`; exposto como `BF.util.fmt/parseTime/secs`). `fmt(x)`: `m:ss.d` abaixo de 1 h e `h:mm:ss.d` a partir dela, arredondando antes de separar (59,96 s vira `1:00.0`, nunca `0:60.0`). `parseTime` aceita `h:mm:ss(.d)`, `m:ss(.d)`, segundos, ponto ou vírgula (em `h:mm:ss` os minutos precisam ser menores que 60). `secs(x)` é a duração por extenso com a vírgula do português (`6,0 s`). O código de tempo mantém o ponto (`0:05.0`, a notação que a linha do tempo e a análise também usam). Teste: `tests/timecode.test.js` (ida e volta e varredura de 57 mil valores).
- **Player e "Ver trecho"** (`BF.player`). `canPlay()` (há vídeo carregado e o Chromium o aceitou), `unplayableMessage` e `playRange(start, end)`, que devolve `false` e avisa quando não toca. Formatos que o Chromium recusa (`.ts` e `.flv` estão no seletor e abrem e exportam normalmente) deixam **Ver trecho desabilitado, com o motivo no `title`**; marcar, salvar e exportar continuam funcionando.
- **Teclado no menu e nas abas internas**. No menu, setas (↑/↓ e ←/→), Home e End só passam pelos itens utilizáveis (sem projeto o item Cortes, desabilitado, fica de fora da volta e Exportações segue alcançável) e a seleção acompanha o foco; nas abas internas de Cortes e de Configurações, ←/→, Home e End (as desabilitadas ficam de fora).
- **CSP**. `default-src 'self'; media-src file: blob:; img-src 'self' data: blob: file:; style-src 'self'; font-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'` (`font-src 'self'` por causa das fontes locais Inter, Montserrat e Material Symbols). O `renderer-base.test.js` confere a política inteira e que nenhuma feature cria `form`, `base`, `object`, `embed` ou `iframe`.
- **Testes e2e** (`tests/e2e/helpers.js`). `stop()` espera **todos** os processos do perfil saírem (o Electron deixa auxiliares segurando arquivos por segundos) e encerra os que sobrarem; `removeDir(dir)` repete por até 30 s, encerra processos que ainda citam a pasta e, se mesmo assim não der, **avisa e devolve `false`** em vez de reprovar um teste que já passou. Novos: `runSecondInstance`, `processesUsing` e `mergeEnv` (no Windows `PATH` e `Path` são a mesma variável; sem isso o ambiente herdado e o pedido viravam duas). Teste: `tests/e2e-helpers.test.js`.
- **Frase de apresentação** (`appInfo.tagline` e README): "Cortes verticais para criadores: analisa, revisa e exporta (a publicação é sua)." (antes "Edição inteligente", que sugeria uma IA que o produto diz não ter).

- **Aba Projetos** (`renderer/features/projects.js/.css`, ordem 5, tela larga, **funciona sem vídeo aberto**; a tela inicial é a Início, logo abaixo). O cabeçalho traz o botão principal **Novo projeto**, que abre a tela Novo projeto (ela não tem item no menu e, aberta, acende este item); com a lista vazia o texto aponta para esse botão e os botões dos cartões são de contorno (a única ação principal da tela é a do cabeçalho). Lista os vídeos que já têm projeto para o usuário saber o que já foi feito e retomar com um clique, em vez de procurar o arquivo. Dados: `project:list` (resumo de cada projeto: `id`, `source`, `meta`, `cutCount`, `counts { pending, approved, rejected }`, `exportedCount` = cortes com ao menos uma exportação concluída, `updatedAt`) mais `fileMissing` (o handler confere se o arquivo do vídeo ainda existe); o projeto completo só é lido ao abrir. Estado de cada cartão: **Novo** (sem cortes), **Em revisão** (há pendentes, ou todos rejeitados), **Pronto para exportar** (aprovados ainda sem exportar) e **Exportado** (todos os cortes, ou todos os aprovados, já exportados). Cada cartão traz a **miniatura** do vídeo (um quadro tirado neste computador; sem ela, o ícone do tipo de origem), que também abre o projeto. Busca (título, canal, jogo, caminho, sem acento), filtros (Todos, Em revisão, Para exportar, Exportados) e **ordem** (Mais recentes, Mais antigos, Nome A–Z, Mais cortes, Mais longos). **Abrir** passa por `BF.openSource` (os ganchos `beforeOpen`/`afterOpen` rodam como sempre) e leva à aba Cortes; se o arquivo foi movido ou apagado o cartão diz "Vídeo não encontrado" e **Localizar vídeo…** copia os cortes e decisões para o arquivo escolhido (`project:adopt`, com confirmação; o projeto antigo continua guardado). **Miniaturas** (`src/core/projects/thumbnails.js`; canal `project:thumbnail { id, path, size, duration }` → `{ state:'ready', url } | { state:'missing' } | { state:'none', reason }`). Um JPEG de 320 px por vídeo, tirado com o **ffmpeg do sistema** (nada de rede, nada baixado) em prioridade baixa, em 10% da duração (entre 5 s e 10 min; vídeo com menos de 30 s usa o meio; duração desconhecida, 5 s; se o instante não render quadro, tenta o começo). Fica em `userData/cache/thumbs/<id>.<chave>.jpg`; a chave vem do caminho, tamanho e duração, então outro arquivo no mesmo nome refaz a miniatura e a antiga sai. No máximo 2 por vez no processo principal, 25 s de prazo cada, pedidos repetidos dividem o mesmo trabalho, o vídeo é conferido com prazo antes (compartilhamento de rede fora do ar não prende ninguém) e quem falhou (sem ffmpeg, vídeo que não abre) só é tentado de novo depois de 1 min (`tools:changed` libera na hora). Vídeo que sumiu continua mostrando a miniatura que já existe. A interface pede só os cartões que aparecem na tela (`IntersectionObserver` na área que rola, com 240 px de folga) e no máximo 3 pedidos juntos; o cache é regenerável.
  **Apagar** (lixeira em cada cartão; `project:deletePreview { id }` → `{ plan }` em números e `project:delete { id, files? }` → `{ result: { projectRemoved, removed, failed, keptSource } }`). A confirmação diz o que sai e o que fica; havendo arquivos do projeto a apagar, traz a caixa **"Apagar também os arquivos do projeto"** (marcada por padrão) com contagem e tamanho. Sempre saem, **o arquivo do projeto por último** (`<id>.json` e as cópias `.bak`/`.corrupt`) e o que o app guarda dele: histórico de decisões, transcrição (e o rascunho), miniatura e o rastro na fila (trabalhos já encerrados do projeto e o registro dos arquivos apagados). Com a caixa marcada saem também (1) os **cortes exportados** que o projeto anotou (`cut.exports[].path`: só caminho absoluto de vídeo que existe como arquivo comum, que não é o vídeo de origem de nenhum projeto e que nenhum outro projeto também anotou, como num "substituir" no conflito de nome) com a legenda `.srt`/`.ass`/`.vtt` gravada ao lado de cada um, (2) a pasta `Cortes` padrão ao lado do vídeo, se ficou vazia (`rmdir` recusa pasta com conteúdo; pasta de exportação escolhida pelo usuário não é tocada) e (3) o **vídeo e o chat que o próprio app baixou**, cuja prova é o registro de downloads da aba Novo projeto apontando para o vídeo de origem do projeto (o registro também é esquecido). **O vídeo do usuário, a legenda que ele importou e qualquer outro arquivo nunca são apagados**, nem por pedido; pasta, atalho e link simbólico também não. O cache da análise é por conteúdo do vídeo e fica (outro projeto do mesmo vídeo o reaproveita). A exclusão é **recusada** (`PROJECT_BUSY`, com a mensagem dizendo onde cancelar) se há exportação do projeto na fila ou em andamento, análise do vídeo ou transcrição em curso: cada handler registra sua verificação em `ctx.busyChecks` e a base consulta `ctx.projectBusy(project)`. Durante a exclusão `project:save` do mesmo projeto é recusado (`PROJECT_DELETING`), para uma gravação atrasada não recriar o arquivo. Tudo é assíncrono e com prazo (`fsGuard`); erros passageiros do Windows (`EPERM`/`EBUSY`/`EACCES`) são repetidos algumas vezes e o que resistir é **listado no aviso final** ("Apague-o à mão") sem desfazer o resto. Se o projeto apagado é o **aberto**, a interface solta antes o histórico pendente (`BF.review.history.discard`), a gravação (`BF.project.discard()`) e o vídeo do player (`BF.player.unload()`: o Windows não apaga um arquivo que o player lê), apaga e **recarrega a tela** (`BF.restart()`) com o aviso guardado (`BF.flash`), para nada do projeto apagado ficar na memória. Projeto com arquivo ilegível ainda pode ser apagado (só os dados dele saem). Novos no `ctx`: `busyChecks`, `projectBusy`, `queue` (`activeForProject`, `forgetProject`), `sources` (`downloadRecord`, `forgetDownload`) e `analysis`; novos no `ProjectStore`: `peekById` (leitura sem efeito colateral) e `remove`.
  Testes: `tests/thumbnails.test.js` (instante, cache, chave, fila, falha, prazo, cancelamento e um JPEG de verdade com ffmpeg), `tests/project-delete.test.js` (store, arquivos do projeto e proteções, "ocupado", projeto corrompido, arquivo preso, canais pelo IPC), `tests/projects-ui.test.js` (cartões, miniaturas, ordem, textos da confirmação e o fluxo do projeto aberto, com um DOM de mentira), `tests/e2e/projects.e2e.js` (lista, estados, miniaturas reais de 320x180, ordenar, busca, filtros, abrir, arquivo faltando e localizar e a lixeira com arquivos de verdade: recusar, com e sem a caixa, vídeo e chat baixados, vídeo sumido e o projeto aberto) e a ordem das abas em `tests/renderer-base.test.js`. Decidido pelo dono (23/10/2026): **não** avisar quando os arquivos exportados de um projeto já não existem na pasta, porque o usuário costuma apagá-los (o aviso de "Vídeo não encontrado" vale só para o vídeo de origem).

- **Aba Geral** (`renderer/features/general.js/.css`, id `general`, ordem 75: a primeira de Configurações; tela larga, **funciona sem vídeo aberto**). É o "Geral" do desenho de Configurações, só com o que o app tem. **Aparência**: Escuro e Claro (cada opção mostra uma janelinha no tema dela), pelo mesmo `BF.ui.setTheme` do botão do rodapé do menu; dentro do Braga Digital Studio o tema é dele (`.theme-locked`) e as opções ficam desabilitadas, com o motivo. **Pasta de projetos**: o caminho que `app:info` informa em `projectsDir` (a do perfil do app; somente leitura) e "Mostrar na pasta" (`shell:reveal`); o texto lembra que o app salva sozinho e que os vídeos e os cortes exportados ficam onde estão. **Sobre**: nome, versão e frase do app (`app:info`) e "Desenvolvido por Braga Dev". **Ficou de fora do desenho** (não existe no app): o item "Sistema" da aparência, **Idioma**, **Alterar** a pasta de projetos, os interruptores **Notificações**, **Salvar automaticamente** (o app já salva sozinho a cada mudança e isso não é uma escolha) e **Enviar dados de uso** (o app não envia nada), os links **Site, Suporte, Discord e GitHub**, as abas **Cortes, Exportação e Atalhos** (as escolhas de revisão e exportação já estão em Preferências) e o usuário "Online". Testes: `tests/general-ui.test.js` e `tests/e2e/settings.e2e.js`.

## 7. Limites conhecidos e o que não foi verificado

- A leitura completa do arquivo para descobrir a duração (último recurso) custa uma passada pelo arquivo; o prazo é 120 s e, estourando, a duração fica desconhecida. O resultado só vale na memória do processo (não é gravado). Medido com MKV e WebM de poucos segundos; **não** foi medido com uma gravação de várias horas.
- A procura do PATH é síncrona (milissegundos nesta máquina). Uma pasta do PATH numa unidade de rede fora do ar ainda pode bloquear o processo principal pelo tempo que o sistema levar para desistir (o `where` tinha o mesmo risco, com prazo de 5 s). **Não verificado** com uma unidade de rede de verdade.
- `.bak` guarda só a **versão anterior** (uma gravação atrás, de 300 ms a poucos segundos). A restauração automática só acontece quando o principal está corrompido; não há tela para escolher entre versões antigas.
- A trava de instância única é a do Electron (por `userData`). Se a primeira instância estiver **travada** (sem responder), a segunda espera cerca de 20 s e encerra sem trazer nada à frente (observado sob carga; a primeira seguiu viva).
- Linux e macOS: o código existe (`processesUsing` com `ps`, `findTool` sem PATHEXT), mas só o Windows foi executado.
- `.ts` e `.flv` continuam no seletor de arquivos (abrem, marcam e exportam; só o player não toca). Um proxy de baixa resolução para tocá-los não foi feito.
